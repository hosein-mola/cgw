# Codex Responses-to-Chat Proxy in Go

## 1. Goal

Build a production-ready proxy in **Go** that allows **OpenAI Codex CLI** to use **DeepSeek V4 Pro** through both:

* ParsPack
* ArvanCloud AI

Codex will communicate with the proxy using the **OpenAI Responses API**.

The proxy will translate those requests to the **OpenAI Chat Completions API**, because DeepSeek V4 Pro is exposed by these providers through Chat Completions rather than a fully Codex-compatible Responses API.

Target architecture:

```text
                  ┌─────────────────────────┐
                  │        Codex CLI        │
                  │ wire_api = "responses"  │
                  └────────────┬────────────┘
                               │
                      POST /v1/responses
                               │
                               ▼
                ┌──────────────────────────┐
                │       Go Proxy           │
                │                          │
                │ Responses → Chat         │
                │ Chat SSE → Responses SSE │
                │ Tool-call translation    │
                │ Error translation        │
                │ Provider failover        │
                └──────────┬───────────────┘
                           │
              ┌────────────┴─────────────┐
              │                          │
              ▼                          ▼
     ParsPack Chat API           ArvanCloud Chat API
     /v1/chat/completions        /v1/chat/completions
              │                          │
              └────────────┬─────────────┘
                           ▼
                  DeepSeek V4 Pro
```

---

# 2. Provider Details

## ParsPack

Base URL:

```text
https://ai.parspack.com/v1
```

DeepSeek model ID:

```text
deepseek/deepseek-v4-pro
```

Use:

```text
POST /v1/chat/completions
```

Do not rely on ParsPack `/v1/responses`.

Observed ParsPack behavior on `/responses`:

```text
object: chat.completion.chunk
```

and final stream termination:

```text
data: [DONE]
```

That is Chat Completions SSE, not a proper Responses API stream.

---

## ArvanCloud AI

Base URL:

```text
https://api.arvancloudai.ir/v1
```

DeepSeek model ID:

```text
DeepSeek-V4-Pro
```

Use:

```text
POST /v1/chat/completions
```

ArvanCloud exposes `/v1/responses`, but DeepSeek V4 Pro currently reports:

```text
There are no available channels for model deepseek-v4-pro
with api type responses
```

Therefore the proxy must also use Chat Completions for ArvanCloud.

---

# 3. Main Design Principle

Codex must see a correct Responses API.

Providers may continue using Chat Completions internally.

The translation boundary is:

```text
Codex Responses API
        ↓
Internal normalized request
        ↓
Chat Completions request
        ↓
Provider
        ↓
Chat Completions SSE
        ↓
Internal normalized events
        ↓
Responses API SSE
        ↓
Codex
```

Do not expose upstream provider quirks directly to Codex.

# 13. Request Translation

Implement:

```text
Responses request
→ Chat Completions request
```

Rules:

## Instructions

Responses:

```json
{
  "instructions": "You are a coding agent"
}
```

Convert to:

```json
{
  "role": "system",
  "content": "You are a coding agent"
}
```

---

## User input

Responses:

```json
{
  "role": "user",
  "content": [
    {
      "type": "input_text",
      "text": "Fix this code"
    }
  ]
}
```

Convert to:

```json
{
  "role": "user",
  "content": "Fix this code"
}
```

---

## Assistant messages

Convert to:

```json
{
  "role": "assistant",
  "content": "..."
}
```

---

## Function call outputs

Responses-style function result:

```json
{
  "type": "function_call_output",
  "call_id": "call_123",
  "output": "file contents..."
}
```

Convert to:

```json
{
  "role": "tool",
  "tool_call_id": "call_123",
  "content": "file contents..."
}
```

This is critical for Codex tool execution.

# 15. Upstream SSE Parser

Providers return Chat Completions SSE.

Typical data:

```text
data: {"object":"chat.completion.chunk", ...}

data: {"object":"chat.completion.chunk", ...}

data: [DONE]
```

Do not assume one TCP read equals one SSE event.

Implement an actual SSE parser.

Suggested API:

```go
type SSEParser struct {
    scanner *bufio.Reader
}
```

Handle:

```text
\r\n
\n
multiple data: lines
partial network frames
empty separator lines
[DONE]
```

Pseudo flow:

```text
read line
↓
collect fields
↓
blank line
↓
dispatch complete SSE event
```

# 17. Responses SSE Writer

Codex expects Responses API SSE.

Implement an event writer:

```go
type SSEWriter struct {
    w      http.ResponseWriter
    flusher http.Flusher
    seq    int64
}
```

Example method:

```go
func (s *SSEWriter) Send(event string, payload any) error
```

Output:

```text
event: response.output_text.delta
data: {...}

```

Always flush:

```go
s.flusher.Flush()
```

after each event.

# 18. Response Lifecycle

For normal text output, emit events in this logical order:

```text
response.created
response.in_progress
response.output_item.added
response.content_part.added

response.output_text.delta
response.output_text.delta
response.output_text.delta

response.output_text.done
response.content_part.done
response.output_item.done

response.completed
```

The proxy must always emit:

```text
response.completed
```

for successfully completed responses.

This is the exact event missing from the current provider implementations.

# 21. Text Streaming Translation

Upstream:

```json
{
  "delta": {
    "content": "Hel"
  }
}
```

Proxy:

```text
event: response.output_text.delta
data: {
  "type": "response.output_text.delta",
  "delta": "Hel"
}
```

Next upstream:

```json
{
  "delta": {
    "content": "lo"
  }
}
```

Proxy:

```text
event: response.output_text.delta
data: {
  "type": "response.output_text.delta",
  "delta": "lo"
}
```

Accumulate full text internally.

At completion emit:

```text
response.output_text.done
```

with:

```text
Hello
```

# 22. Tool Call Streaming

This is mandatory for Codex.

DeepSeek may stream tool arguments across many chunks.

Example:

```json
{
  "delta": {
    "tool_calls": [
      {
        "index": 0,
        "id": "call_123",
        "function": {
          "name": "exec_command",
          "arguments": "{\"cmd\":\"go "
        }
      }
    ]
  }
}
```

Next:

```json
{
  "delta": {
    "tool_calls": [
      {
        "index": 0,
        "function": {
          "arguments": "test ./...\"}"
        }
      }
    ]
  }
}
```

The proxy must accumulate:

```json
{"cmd":"go test ./..."}
```

Maintain state:

```go
type ToolCallState struct {
    Index     int
    ID        string
    Name      string
    Arguments strings.Builder
}
```

Store:

```go
map[int]*ToolCallState
```

# 23. Tool Call Responses Events

Translate tool calling into Responses events.

Emit:

```text
response.output_item.added
```

with an item like:

```json
{
  "type": "function_call",
  "id": "fc_abc",
  "call_id": "call_123",
  "name": "exec_command",
  "arguments": "",
  "status": "in_progress"
}
```

As arguments arrive emit:

```text
response.function_call_arguments.delta
```

Example:

```json
{
  "type": "response.function_call_arguments.delta",
  "item_id": "fc_abc",
  "output_index": 0,
  "delta": "{\"cmd\":\"go "
}
```

At completion emit:

```text
response.function_call_arguments.done
```

Then:

```text
response.output_item.done
```

The final tool item should contain the complete arguments.

---

# 24. Preserve `call_id`

Preserve upstream:

```text
call_123
```

as the Responses:

```text
call_id
```

Do not replace it.

Codex will later send:

```json
{
  "type": "function_call_output",
  "call_id": "call_123",
  "output": "..."
}
```

The proxy must map this back to:

```json
{
  "role": "tool",
  "tool_call_id": "call_123",
  "content": "..."
}
```

If `call_id` changes, Codex tool execution will break.

---

# 25. Tool Execution Flow

The final working lifecycle must be:

```text
Codex sends prompt
        ↓
Proxy sends Chat request
        ↓
DeepSeek requests tool
        ↓
Proxy emits function_call
        ↓
Codex executes tool
        ↓
Codex sends function_call_output
        ↓
Proxy converts result to Chat tool message
        ↓
DeepSeek receives tool result
        ↓
DeepSeek continues answer
        ↓
Proxy emits response.completed
```

This full loop is the core acceptance requirement.

# 28. Client Cancellation

When Codex disconnects or user presses Ctrl+C:

```text
Codex connection closes
        ↓
request.Context().Done()
        ↓
cancel upstream request
```

Use:

```go
req = req.WithContext(ctx)
```

Do not leave upstream DeepSeek requests running after Codex disconnects.

---

# 29. Error Handling

Before streaming begins:

```text
401 → return HTTP 401
429 → return HTTP 429
provider error → 502/503
```

Return Responses-compatible JSON where possible.

Example:

```json
{
  "error": {
    "message": "Upstream provider unavailable",
    "type": "upstream_error"
  }
}
```

---

# 30. Errors During Streaming

Once SSE begins, do not silently close the connection.

Emit:

```text
event: response.failed
```

Example:

```json
{
  "type": "response.failed",
  "response": {
    "id": "resp_...",
    "status": "failed",
    "error": {
      "code": "upstream_error",
      "message": "Arvan connection closed unexpectedly"
    }
  }
}
```

Then close.

Never leave Codex seeing only:

```text
stream closed before response.completed
```

without a meaningful error event.

---

# 31. Provider Failover

For:

```text
deepseek-v4-pro
```

support:

```text
Arvan → ParsPack
```

or configurable reverse order.

Failover allowed only before downstream output starts.

Safe:

```text
Arvan returns 503
        ↓
no Responses SSE emitted yet
        ↓
retry ParsPack
```

Unsafe:

```text
Arvan emits 500 tokens
        ↓
connection dies
        ↓
continue from ParsPack
```

Do not switch providers after content/tool events have been emitted.

---

# 32. Retry Policy

Retry only transient failures:

```text
408
429
500
502
503
504
network connection reset
TLS temporary error
```

Do not retry:

```text
400
401
403
404
invalid tool schema
invalid JSON
```

Recommended limits:

```text
provider attempts: 2
failover attempts: 1 alternate provider
```

Use exponential backoff:

```text
250 ms
500 ms
1000 ms
```

with optional jitter.

Do not retry after downstream streaming starts.

# 37. HTTP Client Configuration

Do not use `http.DefaultClient`.

Create a tuned client.

Example:

```go
transport := &http.Transport{
    MaxIdleConns:        100,
    MaxIdleConnsPerHost: 20,
    IdleConnTimeout:     90 * time.Second,
}

client := &http.Client{
    Transport: transport,
}
```

Do not set a short global timeout that kills long SSE streams.

Instead control lifecycle using:

```text
context deadlines
connect timeout
stream idle timeout
```

# 38. Stream Idle Timeout

Implement an idle timeout independently from total request duration.

Example:

```text
if no upstream bytes received for 300 seconds
→ cancel upstream
→ emit response.failed
```

Do not kill long responses simply because total duration exceeds a fixed small number.

---

# 39. Backpressure

Write events directly to Codex and flush.

Avoid collecting entire long responses in memory.

Maintain only necessary state:

```text
final text buffer
tool argument buffers
response metadata
usage
```

For very large final text, consider configurable limits.

---

# 40. Usage Translation

Upstream may provide:

```json
{
  "usage": {
    "prompt_tokens": 100,
    "completion_tokens": 50,
    "total_tokens": 150
  }
}
```

Translate to Responses usage:

```json
{
  "input_tokens": 100,
  "output_tokens": 50,
  "total_tokens": 150
}
```

Preserve reasoning token details where possible, but do not block completion if provider-specific fields differ.



```text

```

Potential map:

```text

tool_calls → response.completed
```

# 42. `[DONE]` Handling

Upstream providers may end with:

```text

```

Do not forward this directly to Codex.

Treat it as:

```text
upstream transport finished
```

The proxy must then decide the appropriate Responses final event:

```text
response.completed
response.incomplete
response.failed
```

For successful normal completion:

```text
[DONE]
→ synthesize response.completed
```
